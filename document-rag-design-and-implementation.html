借一个文档问答项目，理解 RAG 的完整链路

发表于 2026-07-17 更新于 2026-08-29 分类于 AI 阅读次数： 本文字数： 4.8k 阅读时长 ≈ 4 分钟
基于一个真实的文档问答实现，梳理文件解析、异步任务、文本切片、混合检索、回答生成和引用校验这条 RAG 开发链路。

我原本就在维护一个个人 Go 项目，这里暂且把它叫作「知页」。这个项目主要用来实践和验证一些技术想法，已经具备文件上传、后台任务等基础能力。最近在梳理大模型应用开发时，我想借这个现成的项目，把 RAG、Embedding、向量数据库等概念串进一条真实的开发链路，而不是只停留在各自的定义上。

文档问答正好适合作为切入点：创建资料库并上传文档，等待后台完成解析和索引，再针对当前资料库提问。系统从文档中找到相关原文，让模型据此组织回答，同时返回文件名、页码和引用片段。真正落到代码里，问题也随之变得具体：扫描 PDF 怎么读，长文档怎么切，搜不到时怎么办，模型给出的文件名和页码又能不能相信。

这篇文章不从框架名词讲起，而是借这个已有项目的实际实现，梳理 RAG 从文件上传到可核对回答的完整链路。

这个功能仍是学习和验证性质的实现，只适合资料检索和内容辅助。涉及重要事实与结论时，仍然需要回到原文人工核对。

先明确要解决的问题

最直接的做法，是把文档连同问题一起发给模型。但一个资料库里通常有多份长篇 PDF、Word 文档、扫描件和图片，每次都发送全文会遇到几个问题：

  • 文档可能超过模型上下文限制；
  • 无关内容会增加成本，也会干扰回答；
  • 扫描 PDF 和图片没有可直接检索的文本；
  • 答案很难准确定位到原文件和页码。

因此项目把功能拆成两条链路：

文档处理在上传后执行一次，问答则重复使用已经建立的索引。这也是 RAG 的基本思路：不让模型记住全部文档，而是在每次回答前取回相关原文。

当前项目的整体结构

后端使用 Go 和 Gin。资料库、文档、文本切片、任务和问答记录保存在 MySQL；原始文件暂存在本地对象存储目录；向量索引写入 Qdrant；扫描件通过 OCR 转成文本；最后调用大模型生成回答。

核心数据可以归纳为五类：

数据 作用
资料库 组织文档，也是检索隔离边界
文档 记录文件位置、哈希和处理状态
文本切片 保存正文、页码、顺序和内容哈希
后台任务 记录解析、向量化进度和错误
问答记录 保存问题、回答、引用和检索信息

文档的文本状态和向量状态彼此独立。例如正文已经提取成功，但 Embedding 服务暂时不可用，关键词检索仍然可以工作，不需要把整份文档判定为失败，也不需要重新解析文件。

第一步：上传时只保存文件和创建任务

一次上传大致经过下面几步：

文件不会直接使用用户上传的名称作为存储路径。存储层按用户和资料库隔离目录，并使用 UUID 生成实际文件名。

文件名会先清理，读取时还会通过 io.LimitReader 限制实际大小，避免只相信客户端声明。存储完成后，服务使用实际计算的 SHA-256，在同一用户、同一资料库内查重。

查重分为两层：应用层预检查用于尽早返回已有文档；数据库唯一约束负责处理并发竞争。数据库通过活动文档标识区分未删除和软删除记录，因此同一资料库内正在使用的相同文件只能有一份，而删除后仍可重新上传。

普通重复上传或并发插入冲突时，本次写入的临时对象都会被清理，接口返回已有文档，并将 duplicate 标记为 true。其他数据库错误也会触发清理，尽量避免留下没有记录的孤儿文件。

上传请求到这里就结束，不继续解析 PDF。因为文本文件可能很快，扫描 PDF 却可能需要逐页 OCR；把处理过程放进 HTTP 请求，会让超时、重试和进度展示都很难控制。

第二步：用后台任务完成解析和向量化

后台处理由独立的任务 Runner 负责。

Runner 默认每 2 秒检查一次任务，最多并发处理 3 个任务，每个任务最长运行 2 小时。任务执行期间每 15 秒更新一次心跳，超过 1 分钟没有心跳的 processing 任务会被视为中断任务。

领取新任务前，Runner 会恢复服务异常退出后遗留的任务，并检查文档状态与任务是否一致，补建缺失的解析或向量任务。每个任务都有阶段、进度、错误信息和开始结束时间；panic 也会被捕获并记录，避免任务一直停留在处理中。

任务使用带截止时间的 context.Context。Embedding、OCR、Qdrant 调用和 Poppler 外部进程都会接收这个上下文，因此任务超时或服务停止后，下游工作也能尽快结束。

不同格式最后都会转成同一种结构：

后面的切片、检索和引用不再关心原文件格式，只处理页码和文本。

普通文本文件直接读取为一页。DOCX 本质上是 ZIP 包，解析器读取 word/document.xml 中的 <w:t> 文本，并在段落结束处补换行。

PDF 先通过 Poppler 按页提取文本层。如果整份文档累计至少有 4 个有意义的字母、数字或汉字，就采用文本层；否则进入 OCR。图片则直接交给 OCR。

OCR 没有配置时，文档进入 ocr_required，前端可以明确提示“文件已收到，但当前环境不能识别扫描内容”。PDF OCR 默认最多处理 20 页，避免单个任务无限放大外部调用量。

文件格式的差异到解析层为止。只要统一输出“第几页、什么文本”，后面的 RAG 链路就不需要为 PDF、Word 和图片分别实现。

第四步：切片时保留原文位置

解析后的文本会继续进入切片流程。

切片目标长度是 800 个 rune，相邻切片重叠 100 个 rune。它不会跨页切分，并优先在换行、句号、问号、分号或空白处寻找边界。

每个切片保存：

按 rune 而不是字节计算长度，可以避免中文被 UTF-8 多字节编码错误截断；少量重叠则用于保留落在边界附近的语义。

不跨页会牺牲一点跨页上下文，但能得到更稳定的页码引用。对需要回到原文核对的场景，定位比复杂的切片策略更重要。

切片写入 MySQL 后，关键词检索已经可用。如果启用了 Embedding 和 Qdrant，Runner 会继续创建 document_embed 任务。向量 Payload 带有用户、资料库、文档和切片标识，查询时先按用户和资料库过滤，避免跨资料库召回。

第五步：用混合检索找到相关文档

服务确认资料库归属后，同时执行关键词检索和向量检索。

关键词检索

MySQL 优先使用带 ngram 分词器的全文索引：

查询会限制当前用户和资料库，并且只搜索处理完成、没有删除的文档。

全文检索执行失败或没有结果时，系统把问题拆成 Token：英文和数字按连续词处理，中文生成 2～4 字片段，再使用 LIKE 查找候选。关键词路径擅长匹配名称、编号、日期、金额和原文中的确切用词。

向量检索

向量路径先将问题转换成 Embedding，再到 Qdrant 查找语义相近的切片，更适合处理近义表达和概括性提问。

向量服务不是强依赖。Embedding 未启用、Qdrant 不可用、问题向量生成失败，或者向量结果回查 MySQL 失败时，服务都会记录降级原因，并继续使用关键词结果。

合并两组结果

两条路径各自最多取 30 条，再使用 RRF 合并排名：

RRF 不直接比较全文检索分数和向量相似度，而是根据两份结果中的名次累积分数。一个切片如果在两条路径中都靠前，合并后通常也会更靠前。

结果合并、去重后，前 8 个切片被送入回答流程。这些参数只是当前配置，是否合适仍需通过真实问题和正确引用评测。

问答请求的 context.Context 会继续传给 LLM 客户端。HTTP 调用和重试等待都会监听取消信号，因此用户取消请求或接口超时后，不会继续无意义地调用外部服务。

同时追加“未形成可核验引用”的提示。只有至少一个 chunk_id 属于本次检索结果时，basis_verified 才为 true，前端可以据此区分“模型生成了文本”和“回答带有通过程序校验的引用”。

需要注意，白名单只能证明引用来自本次候选集，不能证明它在语义上足以支撑回答中的每句话。Prompt 负责告诉模型应该如何回答，程序校验负责限制哪些引用可以被接受，两者解决的不是同一个问题。

如果完全没有检索结果，接口会提示文档依据不足。如果检索成功，但 LLM 未启用或调用失败，系统会返回“仅完成文档检索、尚未形成可核验引用”的降级结果；原始检索命中目前不会作为回答直接暴露，也不会伪造引用。

这条链路真正解决了什么

到这里，一个 RAG 应用的主要环节已经串起来：

大模型只出现在最后一段。解析错了，模型看到的就是错的；检索没有找对，模型再强也没有文档可用；引用未经程序校验，回答看起来完整，也不一定能回到原文。

所以 RAG 的核心不只是接入向量数据库，而是建立一条从原文件到可核对回答的数据链。

当前实现的边界

这套实现已经覆盖主链路，但距离生产级知识问答系统仍有明显差距：

  • 引用校验还不等于事实校验。 系统没有最低相关性阈值、无答案分类器和回答—引用一致性检查。模型没有给出有效引用时，回答文本仍会保留，只是降低置信度并提高风险提示。
  • 关键词回退只适合小规模兜底。 LIKE 路径最多取 200 个候选，查询没有稳定排序，前导 % 也难以利用普通索引；数据增多后，性能和召回都可能下降。
  • 删除操作还不是最终一致。 当前按“Qdrant 向量 → 原文件 → 数据库记录”同步执行，任一步失败都可能留下半完成状态。
  • 文档解析仍有资源和格式边界。 混合 PDF 采用整份文档级文本判断，可能漏掉其中的扫描页；DOCX 还缺少解压后 XML 大小和压缩比限制；模型上下文也没有按 tokenizer 做预算。
  • 模型字段没有经过校准。 confidence 和 risk_level 只是模型输出的枚举值，适合界面提示，不适合作为自动决策依据。

这些边界比“回答看起来是否流畅”更重要，因为它们决定系统什么时候应该回答，什么时候应该明确停下来让用户核对文档。

下一步怎么做

下一阶段首先要建立 50～100 个“问题—正确引用”样本，评估正确片段能否进入 Top 3、Top 5 和 Top 8，同时记录无答案识别、引用正确率和检索耗时。在没有评测集之前，很难判断调整切片、增加 Reranker 或更换搜索组件是否真的有效。

围绕评测结果，可以依次补齐：

  1. 增加最低相关性、文档不足判断和回答—引用一致性检查；
  2. 没有有效引用时，明确选择丢弃生成回答或返回原始检索命中；
  3. 加入 Reranker、相邻切片补全和编号、日期、金额等结构化条件；
  4. 将删除改为有状态、可重试的异步任务，并补齐解析和上下文资源限制；
  5. 记录检索降级、无有效引用、请求取消和索引版本等关键指标。

MySQL 仍然适合作为资料库、文档、切片和任务的事实库，需要评估的只是关键词检索组件。数据量不大时可以继续使用 FULLTEXT + ngram；需要更强的中文 BM25、短语匹配和字段加权时，可以引入 OpenSearch / Elasticsearch，或者让 Qdrant 同时承担 Dense 与 Sparse 召回。选择依据应该是评测结果、数据规模和运维成本，而不是技术栈数量。

等检索和引用链路稳定以后，再考虑独立对象存储、敏感文档加密、访问审计、多实例任务调度和全链路监控。只有系统确实需要根据中间结果自主选择工具、继续核验或要求补充文档时，才有必要引入受控的 Agent 工作流；当前固定的 RAG 链路更简单，也更容易测试。

最后

如果只看最终页面，这个功能像是“上传文件，然后问模型”。顺着代码往下看，真正的主线其实是：

解析决定系统读到了什么，切片和检索决定模型看到了什么，引用校验决定回答是否能够被检查。

把这些环节亲手实现一遍以后，再看现成的 RAG 框架，会更容易理解文档加载、切片器、Retriever、向量存储和生成链分别在解决什么，也更容易判断项目下一步真正需要补的是什么。
