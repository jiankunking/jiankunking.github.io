从模型管理到 AI 网关：把资产、流量与成本串成闭环

发表于 2026-10-05 更新于 2026-10-18 分类于 AI 阅读次数： 本文字数： 5.4k 阅读时长 ≈ 5 分钟
模型管理决定谁能用什么、能用多少，AI 网关把授权和配额落实到每次请求。本文沿模型与请求的生命周期，拆解业务面、配置面和数据面的职责，以及用量回流、成本归属和模型下线之间的关系。
AI 网关工程 →

阅读范围 讨论模型平台与 AI 网关的职责划分，沿模型生命周期和请求生命周期组织设计。

先看结论 业务面做决定，配置面交付规则，数据面执行并回传用量；授权、配额和成本要能对应到真实请求。

模型管理决定”谁能用什么、能用多少”，AI 网关把这些决定落实到每一次请求；调用结果再回流，成为分账、扩容和下线的依据。本文沿”一个模型的一生”和”一次请求的一生”两条线，看这个环怎么转。

一、两种事故

做模型平台的人大概都见过这两种事故：

  • 模型已经下线了，还有流量往上打；
  • 申请已经通过了，调用却怎么都调不通。

根子都在同一个地方：管资产的和管流量的是两套系统，各管一半。审批、权限和配额停留在业务系统里，约束不到真实请求；网关能转发流量，却不知道模型为什么上架、谁获准使用、成本算给谁。

传统 API 管理的核心对象是接口，AI 平台管理的核心对象是模型。两者看起来都在处理 HTTP 请求，关心的东西却不一样：

接口管理关心什么 模型管理还要关心什么
地址、协议、认证、路由 模型上架、选型、权限、配额、单价与下线
请求是否成功 输入与输出分别消耗了多少 Token
上游是否健康 实例是否健康、是否还有额度、是否需要切换供应商
调用者是谁 调用属于哪个应用、用户和成本中心

两者真正的关系是一个环：

环上有两个方向：决策向下，模型、权限、配额和路由规则经配置面进入网关；结果向上，Token 用量、调用者和调用结果从网关回到业务侧。

这个环靠三个平面转起来：业务面做决定，管模型资产与使用规则；配置面翻译并交付决定，把业务规则变成网关能执行的路由、实例和插件配置；数据面执行决定并回传结果，以成熟 API 网关为底座，只管请求链路里的鉴权、限流、选路、改写、转发和记录。三个平面各守边界，业务面不碰推理流量，数据面不持资产规则，配置面只做翻译和交付。

难点也在这里：同一个模型、令牌和调用方，在资产系统和流量系统里必须指向同一份东西。接下来沿两条线看这个环怎么转——先是一个模型的一生，再是一次请求的一生。

二、一个模型的一生

用一个贯穿的例子：客服团队要给低代码智能体平台接一个新的推理模型。这个模型从进来到退出，要过六道关：

2.1 选型：先验证，再进资产目录

他们先在模型市场里并排试了几个候选：调 Temperature、Top_p、Max_tokens，也保持参数不变换模型重跑，看效果差异。

选型不只是挑一个模型名，还要判断要不要推理能力、效果要求多高、有没有安全风险。安全风险尤其关键——它直接决定走私有化实例还是云服务，后面的申请和路由方式都跟着变。

2.2 申请：先定归属，再开生产权限

申请单要填使用方式（低代码智能体平台、微服务调用，还是个人办公）和环境（测试还是生产）。

生产权限必须绑定明确场景。没有场景，调用就归不到应用，审计、分账、问题定位都无从谈起。所以申请这一步真正建立的，是模型、调用方、成本归属三者的关系。

2.3 令牌：权限的载体，不是孤立的 Key

一个令牌可以挂多个模型权限，不用一个模型申请一把 Key。令牌的删除边界刻意收紧：删掉最后一个模型权限，令牌随之失效；如果还被智能体引用着，就拒绝删除。系统里不能存在”仍然有效，但不知道由谁使用”的令牌。

申请通过后，规则继续往下走。企业 / 应用路径要签发令牌、创建 Consumer（网关侧代表调用方的消费者对象，凭证和插件配置都挂在它下面）、写入模型权限与配额、加入路由白名单；个人路径只签发令牌，不建 Consumer，鉴权和额度判断由业务侧实时完成。这一步没走完，业务系统里的”已授权”变不成请求链路里的”可以调用”。

2.4 调用：资产关系带进请求

真正开始调用后，SDK 说明只是表皮，底下是模型管理规则在请求侧的表达：

  • RPM / TPM 任一超限就拒绝，保护的是请求频率、模型吞吐和成本预算；
  • 同一对话保持 X-Session-ID 不变，通过一致性哈希尽量落到同一实例，复用 KV Cache；
  • 通过 baggage: sentry-user 传用户信息（baggage 是 OpenTelemetry 随链路传播键值上下文的标准请求头），调用就能关联到日志字段 caller_user，做到端到端归因。

这几个请求头不是业务装饰，而是会话、用户与成本归属进入数据面的载体。

2.5 计费：用量要回到资产关系上

一次用户交互可能触发多次模型调用，只按交互次数或请求数说不清真实消耗，容量和成本还得看 Token 口径。

按 Token 口径统计，能支撑三件事：压测得到单次交互的平均 Token 消耗；分账按令牌归集到应用或子产品；ROI 用 DAU × 单人日均交互次数 × 单次平均 Token 消耗 × 单价 估算日成本。

网关在这里是反馈入口：解析上游 usage，记下输入输出 Token、模型实例、调用者和链路信息，交给配额结算、明细查询和成本分账使用。

2.6 下线：先解除引用，再删资产

模型下线不能从列表里一删了事。已发布路由、已签发令牌、智能体引用、在途迁移都要同步处理。系统用迁移保护名单挡住旧模型继续创建路由，创建时还会校验服务模板兼容性。完整顺序是：先切换调用关系，再回收令牌和路由，最后下架模型资产——反过来，就是开头那两种事故。

六个阶段到这里并没有真正结束。图 3 的两条虚线就是回流：下线腾出的位置由替代模型补上，进入新一轮选型；用量与状态则持续修正配额、扩容计划与供应商取舍。

三、一次请求的一生

模型的一生负责建立和改变资产关系；一次请求的一生，是这些关系在毫秒到分钟级的链路里生效的过程。

低代码智能体平台正式接入后，企业路径的每个请求进网关，网关都要依次回答五个问题：

  1. 你是谁：校验企业凭证。
  2. 你能否调用这个模型：检查模型权限与路由白名单。
  3. 这次请求发到哪里：过滤不健康或额度耗尽的候选实例，再完成选路。
  4. 这次请求能否放行：对选中实例执行 Token 预检与 RPM 限流。
  5. 最终用了多少：解析响应 usage，写日志并回传业务侧。

身份和权限要先确认，实例要在转发前选定，真实用量只能在响应后结算。实现可以变，这个先后不能乱。

这五个问题背后都是第二章的决定：你是谁，来自申请建立的归属；能否调用，来自令牌权限；发到哪里，来自选型与下线确定的实例清单；能否放行，来自配额结论；用了多少，回到计费口径。两条线就在这里咬合。

3.1 两类调用方，两条链路

低代码智能体平台走企业路径，个人办公走个人路径。两类调用方的数据来源不同，塞不进同一套鉴权模型：

  • 企业 / 应用路径：令牌绑定固定调用方，网关本地完成身份、模型权限和配额检查。
  • 个人路径：不创建固定消费者对象，由业务侧实时校验令牌与额度，请求结束后回收实际用量。

两类调用走不同的场景域名。请求到达网关时，域名已经决定它命中企业路由还是个人路由，不是进门之后再由路由标签二选一。

3.2 用量只解析一次

网关只解析一次上游响应里的 usage，同一份结果同时交给 Token 配额结算、个人用量上报、日志和指标，避免各算一遍导致口径不一致。

这一步把”请求成功”变成了可运营信息：不光知道调用完没完成，还知道用了哪个实例、烧了多少 Token、算在谁头上。

请求体和响应体可能带着提示词、业务数据甚至个人信息，”能记录”不等于”默认全量留存”。生产环境还要按场景决定是否采样，并配套相应的脱敏、访问控制和保留周期。

3.3 一次真实的请求

图里实例 C 因为主动健康检查失败，已经移出候选。这次请求先到了实例 A，A 返回 429——它只在本次请求中被排除，不会写进健康检查状态。Fallback 开着、距上次失败还没超过重试时间窗、重试次数也还有，选路器接着选了实例 B。低代码智能体平台全程无感：不用自己重试，也不用换地址换凭证。

如果实例 A 持续异常触发告警，告警联动会把它的优先级置 0，后续流量不再选它，等告警恢复再还原。请求级排除、健康检查摘除、告警降权，三种机制互不干扰。这些机制怎么串起来的，是下一章的主题。

四、环转起来的三个场景

配额、可用性、配置——每个场景都是同一个环：决定向下，结果向上。

4.1 配额：业务侧计算，数据面执行

业务侧掌握模型权限、套餐和成本规则，适合回答”应该给多少”；数据面看到每一次真实请求，适合回答”已经用了多少”。两者不能互换。

企业 / 应用路径用四步链路把它们接起来：

核心边界一句话：企业路径下，网关不持有配额规则，只持有计算后的结论。 个人路径更彻底，鉴权和额度判断都在业务侧实时完成。

Token 限流分两段：转发前看还有没有余量，响应后按真实 usage 入账。这样调用前能拒绝、调用后能按实际结算；代价是并发在途的请求没有预留额度，实际用量可能短时超过阈值。

对用户来说，这套实现最后只表现为两类信息：限流维度是 RPM / TPM，性能档位有标准模式 / 高性能模式等，具体数值以模型市场详情为准。时段限流也一样，时段是请求到来时读取的变量，不是每天定时批量改线上配置——这个能力已经上线，忙闲时额度在运行时按同一套规则切换。

4.2 可用性：实例池自动绕开故障

一个模型可能同时对应自建实例、云服务和备用供应商。转发前，健康状态、剩余额度、告警降权共同决定实例能不能进候选；转发后，上游 429/5xx 按重试条件触发候选切换。这些条件必须收敛到同一条选路与重试链路，否则健康检查刚摘掉的实例可能被另一套逻辑重新选中，配额耗尽的高优先级实例也可能继续收到流量。

上一章那条请求就是这么走的：三种排除机制虽然各自独立，作用的却是同一个候选池——高优先级的 A 不可用，请求就落到了 B。

4.3 配置：数据库是真源，下发只是交付

模型权限、配额和实例状态都会变，但变化不能靠全量覆盖网关配置来完成——一次业务下发就可能冲掉运维的手工调整。

所以配置环节只守两条边界。真源边界：受管插件以数据库为唯一真源，非受管插件保留数据面现状；数据库事务提交后再调用网关，外部 IO 不进事务。失败边界：下发失败就记录状态、告警并重试，不用数据库回滚掩盖”未送达”；真要回滚，先恢复网关、再回滚数据库。

配置面只改目标字段，下发后回读确认。追求的不是某次调用绝不失败，而是失败后仍知道真源在哪，数据面能重新收敛。

A–G 是网关侧能力，覆盖一次请求的执行及其运行保障；H 是资产链，回答一个模型从哪里来、给谁用、何时退出。细项都在图 1 里，不再重复列。

结合现有代码与配置资料，主链路已经覆盖模型路由、四个作用域的限流、SSE、请求改写、健康检查、Fallback、基础日志指标和多地域接入。还有几处边界没有到位：

能力 当前边界
内容审核 已预留接入位置，但尚未形成完整的消费者级、请求与响应双向审核能力
协议转换 已具备部分方向的转换能力，OpenAI 与 Anthropic 双向透明转换仍需补齐验证
可观测性 Token、延迟和 TTFT 已有基础；输出 TPS 指标尚待建设，部分业务字段需要自定义配置
证书自动更新 属于目标能力，现有材料尚未定位到实现证据

这张图最重要的不是功能数量，而是边界：A–G 决定请求如何执行，H 决定为什么这样执行。传统 API 网关主要覆盖前者；要让模型成为一等公民，后者必须由模型管理与业务控制面补齐。

归位时我只用一条规则：每项能力都要有明确的执行方、输入和输出；找不到责任边界的，先记为缺口，而不是先做成一个菜单项。

六、反馈如何变成决定

运行结果会从三个地方往回走：

回流的触发 谁接住 改变什么决定
上游 429 / 5xx 持续出现并触发告警 数据面告警联动降权 实例的选路优先级，直接影响后续每一次选路
Token 用量与调用明细 配额与分析层 分账归集到应用或成本中心，并支撑容量与成本口径（2.5）
实例健康状态与用量增长趋势 运维与模型运营 扩容实例、降级或补充供应商，直至进入 2.6 的下线与迁移

第一行不需要人参与：状态一变，选路优先级跟着变。后两行要人拍板：数据先变成账单和看板，再决定扩容、换供应商或下线。

回到开头那两种事故：模型下线了还有流量、审批通过了调不通，根子都是资产关系和真实流量脱节——决定传不下去，结果也回不来。这两条线跑通之后，”谁能用什么、能用多少”才不是一次审批就锁死的台账，而是随运行结果不断修正的决定。

结语

模型管理决定”谁能用什么、能用多少”，AI 网关负责把这些决定落实到每一次请求；请求结束后，用量、调用者和调用结果再回到模型管理，支撑分账、扩容、迁移与下线。

这也是两条主线的交点：一个模型的一生负责建立和改变资产关系，一次请求的一生负责执行并验证这些关系。少了前者，网关不知道为什么这样转；少了后者，模型管理里的权限和配额只是纸面规则。

能力图谱的价值不在于列出多少功能，而在于让每项能力都能找到执行位置、输入、输出和反馈路径。这几件事连起来，模型资产、流量治理与成本管理才构成真正的闭环。

作者的话

这套系统从能力盘点、三平面架构设计，到自研插件、模型全生命周期、限流迁移与运维台，都由我负责推进落地。把散在不同系统里的实现放到同一张图上后，一件事变得清楚：”管资产的””算配额的””数请求的”必须各守边界，又能通过控制与反馈两条链路相互闭合。
