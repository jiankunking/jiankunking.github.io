APISIX 多进程架构：优势、缺点与适用边界

发表于 2026-11-12 分类于 Architecture 阅读次数： 本文字数： 7.3k 阅读时长 ≈ 7 分钟
从两张架构图理解 APISIX 的多 worker 与协程模型，分析本地副本、shared dict 读锁、事件循环和资源隔离，再讨论 AI 流式代理的适用场景与压测重点。

APISIX 用 Nginx 多进程处理连接，在 worker 内运行 Lua 协程，通过本地缓存和共享内存管理状态。这套组合支持动态配置和插件扩展，但也带来了副本、同步和调度成本。

下面从两张架构图看起，先说明 worker 之间如何共享状态、worker 内的请求如何执行，再讨论这些机制对 AI 流式请求的影响。

1. 先看架构：哪些东西共享，哪些不共享

master 管进程，worker 处理请求

APISIX 构建在 Nginx/OpenResty 之上。master 负责启动和管理 worker、处理信号等工作，业务请求不是先进入 master，再由它转发给 worker。

多个 worker 是多个独立进程。每个 worker 有自己的地址空间、LuaJIT 运行时、模块变量和本地缓存。普通请求处理主要运行在各自的单线程事件循环中，多个 worker 可以在不同 CPU 核上并行工作。

图中省略了辅助进程和具体配置同步组件。需要注意三点：

  1. worker 之间不共享普通 Lua 对象。 一个 worker 修改模块变量，不会自动改变其他 worker 的变量。
  2. 共享字典是另一个存储空间。 多个 worker 映射同一共享区，通过相应 API 访问；它不是一个所有进程都能直接操作的 Lua table。
  3. 进程隔离不等于资源完全隔离。 worker 仍共用机器的 CPU、内存和网络，也可能访问同一共享字典。

跨 worker 的状态共享：shared dict 与其他方式

共享内存是一块多个进程都能访问的存储空间，shared dict 是建立在这块空间上的一种数据结构。 两者不能画等号，shared dict 也不是跨 worker 共享状态的唯一方式。

对于普通 Lua 插件，lua_shared_dict 是 OpenResty 内置、最常用的跨 worker 键值容器，也支持原子计数和列表操作。它共享的是字典条目，不是任意 Lua 对象；其内部结构和锁机制在第三节展开。共享范围通常是同一 Nginx 实例，不会自动跨多个网关实例同步。

在 Nginx 底层，C 模块可以申请共享内存区，实现计数器、队列、树等结构。一些限流、缓存机制就是如此，但并不通过 Lua 的 ngx.shared 字典访问。它们各有自己的同步实现，不能一概套用 shared dict 的字典级锁结论；Lua 插件要访问这些结构，通常需要专门的模块或绑定。

跨 worker 交换状态还可以使用 Unix socket 等 IPC，或 Redis 等外部服务。这些属于通信或外部存储，不是让多个 worker 直接共享同一个 Lua 对象。

worker 内部：协程在同一主线程上执行

请求进入 worker 后，路由匹配与插件逻辑在相应阶段执行。Lua 协程配合 Nginx 的事件机制，在等待网络等可让出的操作处挂起，让其他请求继续处理。

协程并发与 CPU 并行是两回事。 一个 worker 可以同时维持很多进行中的请求，但普通 Lua 请求代码并不是在这个 worker 内同时使用多个核执行。

Lua timer 回调也在 worker 中执行，不是独立后台线程。FFI 不会自动把调用异步化。OpenResty 虽有辅助线程等能力，普通 Lua 插件并不会自动使用它们。

请求、配置与状态是不同路径

常规 HTTP 代理依赖 Nginx 的上游和输出机制，APISIX 在各阶段执行路由与插件。部分插件使用 cosocket 自行读取和转换响应，后文会单独讨论这条路径。

在常见的 etcd 部署方式下，APISIX 会把配置同步到各 worker，请求处理时主要读取本地配置，而不是每次访问 etcd。具体同步路径取决于版本和部署模式。

状态范围 典型内容 谁能直接使用
请求内 ngx.ctx、解析结果 当前请求的处理逻辑
worker 内 模块变量、lrucache、配置对象 同一个 worker 内的请求与任务
共享内存 部分计数、限流状态、指标条目 映射该共享区的多个 worker
外部系统 etcd 配置、外部缓存 通过同步或网络访问取得数据

2. 这套架构的优势

连接处理。 Nginx 的事件驱动模型适合大量并发连接，OpenResty 提供 Lua 执行与非阻塞网络 API，LuaJIT 降低许多 Lua 计算的开销。

本地处理。 常用配置和缓存留在 worker 内，减少了路由匹配与对象读取的共享访问；多个 worker 则可以利用多核。

动态配置。 路由、上游和常用插件配置可以在运行中更新，不必每次 reload Nginx。路由多、变更频繁时，这比每次修改都重载进程更方便。

插件开发。 Lua 插件可以复用网关阶段和已有能力，cosocket 允许用接近同步代码的方式组织非阻塞 I/O。很多业务策略不必下沉到 C 模块。

3. 多 worker：本地副本与共享锁

每个 worker 都要维护自己的本地状态

回到第一张图，每个 worker 都有本地缓存。根据同一份配置构建的对象和热点缓存，可能在多个 worker 中分别创建；cosocket 连接池通常也是 worker 级的，一个 worker 的空闲连接不能直接供另一个 worker 使用。

增加 worker 数，可能同时增加缓存副本、空闲连接和初始化工作。流量分布不均匀时，各 worker 的缓存命中率和连接复用效率也可能不同。

这并不意味着所有内存都按 worker 数线性增长：共享页、共享字典和独占对象要分开看，也不能把各 worker 的 RSS 简单相加。连接池容量则主要约束池内保留的空闲连接，不能直接当作活跃连接总数上限。

shared dict 如何组织共享状态

限流、计数和缓存有时需要跨 worker 共享，不能各算各的。shared dict 可以避免每次访问外部服务，但也需要协调多个 worker 的读写。

接口像字典，底层却不是 Lua table，也不是普通哈希表。 它的主要组成包括：

内部组成 作用
条目节点 保存 key、值类型、value、过期时间等信息
红黑树 按 key 的哈希值和 key 内容组织节点，用于查找条目
LRU 队列 记录最近访问顺序，在需要淘汰时优先考虑较久未访问的条目
slab 内存分配器 在配置的共享区中为条目分配和回收空间
字典级互斥锁 协调多个 worker 对上述结构的访问和修改

常见的 get、set、incr 等操作会获取字典级互斥锁。不同字典有各自的锁；同一字典内，即使访问不同 key，也可能竞争。

为什么 shared dict 读取也要加锁？

读操作加锁，不是为了防止它修改 value，而是为了防止其他 worker 在它读到一半时修改或删除数据。 共享内存只保证多个进程能访问同一块内存，并不自动保证一次字典读取的完整性。

所以，读取期间需要保证查找路径和节点仍然有效，值也不会在复制到一半时被修改。shared dict 的锁保护的不只是某个 value，还包括内部红黑树、队列和节点生命周期。

只给写操作加锁，为什么不够？ 锁不是给整块内存自动套上一层保护罩，它只能约束同样会获取这把锁的操作。写操作拿着锁时，一个根本不拿锁的读操作仍然可以访问内存，读写依然可能同时发生。因此，当前实现让读写双方都获取同一把锁：

锁只保护这一次读取；get 返回后，其他 worker 仍然可以更新字典。

那为什么两个读取也会竞争？ 因为业务上的“读”，在 shared dict 内部还包含“写”：查找到有效条目时，会把它移到 LRU 队列前面，记录最近访问顺序，供后续淘汰使用。

两个 worker 即使读取不同 key，也可能同时修改同一条 LRU 队列。当前实现使用字典级互斥锁，因此读读也会互相等待。由于读取包含内部写操作，仅换成读写锁并不能让它们直接并行。

锁由 shared dict API 内部获取和释放，调用者不需要为了执行一次 get 再手动加锁。不是共享内存天然要求读加锁，而是 shared dict 当前的实现需要这样做。 只读共享数据、原子变量，或专门的无锁读取与安全回收机制，可以采用不同设计。

锁竞争如何影响 worker

当共享访问较少时，这笔成本通常可控；当多个 worker 高频访问同一字典，或者成批遍历共享条目时，增加 worker 也会增加竞争者。扩展性此时取决于共享访问比例，而不只是 CPU 核数。

这种锁等待不会像 cosocket 等待网络那样挂起 Lua 协程。竞争严重时，调用所在的 worker 无法及时处理其他请求。get_keys(0) 会在持锁期间遍历整个字典，不宜在请求路径或高频 timer 中对大字典反复执行。

本地副本减少了共享读取，却需要处理失效、版本变化和同步。增量更新可以摊薄工作量，全量重建则可能产生较大的单次开销。

计数器也可以先在 worker 内累计增量，再由 timer 批量同步到共享字典，以减少共享更新次数。这种做法需要接受同步延迟，并处理同步失败。

单次操作原子，不等于多步逻辑原子

incr、add 等单次操作提供原子语义，不代表多个 API 调用组成的逻辑也成为一个事务。多个 worker 仍可能在调用之间交错执行。

例如，用 get 后接 set(value + 1) 更新计数器，两个 worker 可能都读到 10、都写入 11，丢失一次增量。单 key 计数应使用 incr；多 key 或跨字典更新仍需额外协调。

同一 worker 内也有类似问题：如果把请求临时状态放进模块变量，协程 yield 后，其他请求可能覆盖它；恢复执行时，读到的就不再是本请求的状态。

4. 长计算为什么会拖慢整个 worker

第二张图中，多个请求最终使用同一个主事件循环。一段长时间不让出执行权的 Lua 代码，会延迟这个 worker 上其他请求的处理，即使那些请求与它没有业务关系。

大 JSON 解析、复杂匹配、长循环、共享字典扫描，都可能产生这种影响。LuaJIT 可以让许多计算更快，但不会让长计算自动让出执行权。

循环里有 cosocket 读取，也不保证每轮都会让出。 数据已经在缓冲区时，读取可能立即返回，随后连续解析、拼接、统计，仍可能长时间占用 worker。

加入 ngx.sleep(0) 可以增加其他协程获得执行机会，但不减少总计算量，也不是严格的公平保证。更根本的处理是减少重复工作、限制单次批量规模，必要时把重计算移出普通请求执行路径。

timer 通常由各 worker 分别创建。如果任务只需要在实例内执行一次，例如一次共享字典扫描，就要避免所有 worker 重复扫描；用于同步各自本地增量的任务，则需要每个 worker 分别执行。无论哪种任务，都应限制单次处理量，避免长时间占用事件循环。

这对尾延迟尤其重要：平均吞吐可能正常，少量重任务却已经让同 worker 的轻请求变慢。

5. shared dict 的容量、过期与淘汰

shared dict 无需网络往返，但容量由配置确定，条目不由 Lua GC 回收。

复杂对象放入共享字典通常需要编码与解码；留在 lrucache 中可以直接使用 Lua 对象，但需要在各 worker 分别保存。

条目过期，不等于空间立即回收

TTL 到期后，普通 get 不再返回该条目的值，但它占用的空间不一定立即释放。回收可能发生在后续访问、写入或显式清理时。

组件维护的索引、版本记录或本地引用还需要单独清理。经历反复生成、过期、重建后，应检查内存和维护工作量是否持续增长。

容量规划不只看当前有效条目数，还要看条目更替速度、键长度、分配开销，以及组件额外维护的索引。

以 Prometheus 指标为例，一个标签组合可能展开成多条序列：经典直方图有 B 个有限桶时，加上 +Inf 桶、sum 和 count，通常对应 B+3 条序列。如果指标库将这些序列存入共享字典，实际容量还取决于存储方式和额外索引。长标签也会增加键的存储成本，不能只按业务对象数量估算空间。

空间不足时，成功写入也可能有代价

普通 set 在必要时可能强制淘汰尚未过期的条目，并返回 forcible=true；safe_set 避免这种强制淘汰，空间不足时可能失败。

写入成本也取决于条目是否需要创建。不断写入新 key，需要分配内存、更新红黑树和 LRU 队列；容量紧张时还可能触发回收或淘汰，增加持锁时间。同样的写入频率，更新已有计数器与持续创建、过期、重建条目，开销可能明显不同。

指标、限流和缓存对丢失的容忍度不同，不能只看写入是否成功，还要检查是否淘汰了其他有效条目。

free_space() 统计空闲页空间；已经分配的页内还可能有可用槽位，而新条目能否写入也取决于分配规格，因此它不是精确的剩余可写容量。

共享区大小不能像路由配置那样热更新，调整时需要确认目标版本对 reload 和共享区重建的要求。如果索引持续增长或旧条目无法有效清理，扩容也只是延后耗尽时间。

6. 插件与租户之间没有独立的资源配额

鉴权、请求转换、流式解析和部分指标维护，可能共用一个 worker 的执行资源。即使指标使用独立字典，其维护任务仍可能占用业务请求所在的事件循环。

进程隔离保护的是 worker 之间的地址空间，普通 Lua 插件没有因此获得独立的 CPU 配额或内存预算。不同租户的请求也一样：租户 A 长时间计算时，租户 B 的轻请求可能等待。入口限流控制进入的请求数量，无法保证每个请求的计算成本相同。

要求强隔离时，可以按租户或负载拆分实例，并配置资源配额，代价是额外的资源和运维工作。仅改成多线程或可抢占调度，并不会自动获得租户 CPU 配额。

7. 配置热更新也有传播时间

新配置需要同步到数据面、更新本地对象，并使旧缓存失效。多个 worker、多个实例应用更新存在传播过程，其间可能短暂使用不同版本；集中重建缓存也有开销。要求跨路由、跨实例同时切换的业务，需要验证目标部署是否提供相应保证。

路由配置、Lua 代码、底层 Nginx 配置和共享内存容量，也不属于同一种更新机制。涉及进程更替的升级还需要规划长连接排空和旧 worker 的退出，而不只是确认新实例启动成功。

8. AI 流式请求需要额外关注什么

直接转发与逐片段加工

等待上游时，worker 可以处理其他请求，大量模型请求不必对应大量请求线程；但每条连接仍占用文件描述符、缓冲区和请求状态。如果只是转发并改写少量鉴权信息、模型名称或请求字段，处理逻辑通常较轻。逐片段解析和加工内容则会持续增加 CPU 工作量。

直接代理 SSE，较多复用 Nginx 的代理和输出机制，需要正确配置超时与缓冲。自行读取 SSE、逐事件解析、修改内容、统计用量、再重新输出，则需要插件控制单轮解析量和消息暂存上限，在下游变慢时放慢读取，取消后停止上游活动，并区分“暂时无完整消息”和“连接失败”。

普通代理的吞吐不能直接代表流式加工的性能，测试应使用实际启用的插件与处理路径。具体可关注：

AI 负载特征 对应的架构边界 需要关注的影响
长上下文、大型 tools JSON 解析与转换占用 worker 执行时间 重复 decode、分配和 GC 压力
密集小片段输出 读取、解析循环增加 单次连续工作量、其他请求的尾延迟
长时间流式连接 已建立的连接通常持续由原 worker 处理 worker 间负载差异；新开 worker 不会直接迁移正在处理的流
慢客户端、中途取消 自定义流式路径需要背压和清理 缓冲上限、上游是否及时停止、资源何时释放
模型、路由、消费者等指标维度 共享状态有容量和维护成本 实际标签组合、桶数、序列更替和同步工作量
多租户混合负载 请求共用 worker 的执行资源 重请求对其他租户的影响，见第六节

连接时间长本身不会让 CPU 持续繁忙。等待、计算、缓冲和共享状态维护，需要分别测量。

AI 容量评估不能只看 QPS

在稳定状态下，在途请求数大致等于请求到达率乘以平均持续时间。每秒进入 20 个请求、平均持续 60 秒，对应约 1,200 个在途请求。

除 QPS 外，还应观察在途流数量、每个 worker 的 CPU、请求体大小、分片处理频率和缓冲占用。首字延迟与输出间隔受模型上游影响，应对照直连上游或基线代理，辨别网关增加的开销。再加入慢客户端、取消和轻请求混跑，检查缓冲是否受控、上游是否及时停止、轻请求是否被拖慢。

9. 从架构判断适用范围

如果主要工作是等待上游响应、本地配置读取和简单改写，APISIX 比较合适。大量共享更新、重计算和持续流式加工，则需要重点检查锁竞争、事件循环阻塞和租户间相互影响。

上线前比较不同 worker 数下的吞吐、尾延迟、独占内存和连接复用，并让状态测试覆盖多轮过期、清理和重建。短时压测容易漏掉历史状态积累的成本。

增加 worker 能分担请求，却不一定能解决共享锁竞争；把任务放进 timer，也不会让它脱离 worker 的事件循环。遇到性能问题时，应先确认时间花在计算、锁等待还是网络等待上，再决定如何调整。

  • 11 月共享字典满：存活序列约 3.9 万至 4.6 万，剩余空间仍持续减少，提示容量评估还需要检查历史条目和维护索引，不能只看当前序列数。具体占用原因尚未完全确认。
