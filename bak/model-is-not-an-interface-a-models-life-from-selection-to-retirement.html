模型不是接口：一个模型从选型到下线的一生

模型不是接口，是资产。本文跟完一个模型在企业里的六段旅程——选型、申请、令牌、调用、计费、下线，每段一个判断，附上被否决的替代做法；AI 网关是“调用”与“计费”两环的载体，从三平面、裁决与执行分离、候选池、时段到配置真源，五个判断全部落到具体机制上。

接口定义一次、长期有效；模型会上新、会下线、会因为合规从云服务切到私有化、会被分账到子产品。模型是资产，不是接口。 本文跟完一个模型在企业里的一生——选型、申请、令牌、调用、计费、下线六段旅程，每段讲清一个判断，和被它否决的替代做法。托住这条链的是一个 AI 网关，它是”调用”与”计费”两环的载体。判断是通用的，证据不是：开源部分均可在上游源码中自行验证；内部材料只取稳定的流程性结论，易过时的数值一律不写。

本文与往期：网关系列里，本篇是唯一一篇”全景 + 落点”型的，其余都是切片。要标准，读《什么样的网关，才算好的 AI 网关？》；要另一种限流形态，读《大模型网关限流新思路：从进程内漏桶到分布式漏桶矩阵》；协议转换的单点深挖在《AI 时代高效设计开发：Anthropic → OpenAI 协议转换插件实战》；生产排查在《一次升级引出两个独立缺陷：API7 AI 网关流式 500 与低流量 CPU 打满排查》。

正文三章只讲判断与取舍；能力核对表收进附录，想复核时再去。

一、三个假设：调用与计费两环的三堵墙

模型的一生走到第④⑤段（调用与计费），就绕不开一个流量系统。而现成的流量系统——不管是哪条路线——对 AI 场景有三个没说出口的假设：

传统 API 网关的假设 AI 场景的现实
计费单位是请求次数 计费单位是 token，一次请求可能是 100 也可能是 100000，而且要等响应回来才知道
上游是自己的服务 上游是第三方模型服务，会 429、会超时、会半夜挂掉，还会悄悄改协议
一次请求几十毫秒返回 单次推理可能几十秒，流式响应持续几分钟，body 还可能膨胀到几十 MB

而且对 Kong、APISIX 这类基于 OpenResty 的底座，这三行不只是清单问题，而是架构问题：nginx 的 limit_req、APISIX 的 limit-count，单位都是请求数，访问日志也按请求落行，而 AI 要数的是响应回来才知道的 token。原生的限流和计量，单位从一开始就是错的。第三章 3.2 节的四层限流，补的就是这件事。

这三堵墙叠起来是前三个问题：第一堵（计费单位）给出问题一，第二、三堵（上游是谁、要跑多久）给出问题二——“这次请求还能不能转”；而这两件事都得靠不停改配置去追，改得越频繁，下发冲掉手工改动的机会就越多，问题三由此而来。问题四不来自这三堵墙，它来自开头那句话——模型是资产。

问题一：配额怎么算？”每个令牌对每个模型的 TPM 限 20 万”拆开是三个维度：令牌、模型、时间窗。配额的计算发生在业务系统里（申请令牌时就定好），计数必须发生在数据面（请求真正经过的地方）。两者之间的距离，就是绝大多数限流方案设计崩坏的地方。

问题二：实例挂了怎么办？一个模型背后往往挂着自建推理集群、云厂商 SaaS、备用供应商。健康检查挂了要摘除、配额用完要跳过、上游返回 429/5xx 要换一个重试、告警响了要临时降到零——这四件事必须共用同一套候选池，否则就是四套互相打架的逻辑。

问题三：配置怎么保证不覆盖别人的改动？网关的配置有两份真源：数据库里”应该是什么样”，和数据面上运维手工改过的”现在是什么样”。每次下发都可能把数据面的手工调整冲掉。这不是理论风险，是所有用过配置下发的团队都踩过的坑。

问题四：模型本身怎么管？一个令牌可能挂着多个模型权限，用量要分账到子产品；申请时选的限流档位，最后要真的变成网关上的一个数字。流量层解决”这次请求怎么转”，资产层解决”这个模型给谁用、花多少钱”。缺了后者，网关只是一个高级代理。

前三个决定请求怎么走，第四个决定这套系统能不能长期运营。先回答第四个。

二、模型的一生：六段旅程

网关只解决”请求怎么转”，但请求之前和之后还有一连串问题：这个模型从哪来？谁能用？花了多少钱？下线了怎么切？

我把用户视角的完整旅程收敛成六个阶段（流程描述来自对外的《模型使用手册》）：

① 选型

被否决的做法是照着榜单和厂商演示拍板定模型。我的判断是把选型改成跑实验，一个当天就能跑完的实验：模型市场里就能开跑，最多 3 个模型并排对比，Temperature / Top_p / Max_tokens 可调着做 A/B，换模型、不换参数、直接重跑。这一轮只算初筛，把明显不合适的先排掉，不是拍板的依据。

选型原则最终收敛成三档：要不要推理（*-thinking 系列 vs 非推理系列）、效果要求（高/适中/特定训练）、安全风险（私有化 vs 云服务）。最后一档直接决定后面走哪条申请链路——选型不是挑个名字，是在挑这条链的入口。

② 申请

被否决的做法是先给权限、归因后补。

申请表单是一个二维矩阵：使用方式（低代码智能体平台 / 微服务调用 / 个人办公）× 环境（测试/生产）。测试环境的权限在团队内共享、带限流，只用于开发调试。

为什么”生产必须先有场景”？没有场景就没有归因，没有归因就没法审计、分账，出了问题也定位不到应用。

③ 令牌

被否决的做法是每个模型申请一个 key——模型一多就是 key 泛滥。

我的判断是一个令牌挂多个模型权限。配套规则有三条：谁能看完整令牌、谁能删、谁能删掉单个模型权限，各有各的边界；删掉最后一个模型权限，令牌跟着失效，删之前先看有没有智能体在引用它，有就拒绝；令牌必须关联到智能体。

这些规则背后是同一个目的：系统里不能存在”活着但不知道给谁用”的令牌。

令牌签发之后，还要变成网关上的一串配置——下发 Consumer、注入限流变量、把 Consumer 加进路由访问白名单。这是令牌这一段接进网关的地方，三步都在数据面上执行，见 3.1 与 3.2。

④ 调用

手册里的用户须知，和网关实现完全对得上：

手册怎么告诉用户 网关里的实现
限流按 RPM / TPM 双维度，超出任一触发 四层限流的模型级默认组 → 令牌快照 → 注入 → 计数
请求头带 X-Session-ID，网关会路由到同一推理实例以复用 KV Cache 按请求头做一致性哈希，同一会话固定到同一实例
登录用户用 baggage: sentry-user 端到端透传，模型网关解析关联 解析后写进日志字段，供端到端关联

会话亲和的收益在 KV Cache 命中，多轮对话上下文越长越划算；手册那条”同一对话保持 Session ID 不变”的建议，其实是把网关配置翻译成了用户侧调用规范。

这一段的执行细节全部在第三章。

⑤ 计费

手册里的这个判断是整套成本体系的起点：

用户与助手的一次交互，可能触发多次模型调用——因此传统的并发量预估方法失效了，需要以 Token 作为压测与成本的评估基准。

被否决的做法是按并发量或请求数估成本——请求次数和钱之间已经没有稳定比例。

由此推出三件事：压测有了口径，跑出”单次交互平均 Token 消耗量”；分账有了口径，按令牌的 Token 用量分到子产品、每月出账；ROI 也有了算式：DAU × 单人日均交互次数 × 单次平均 Token 消耗 × 单价 = 日成本。

这解释了四层限流为什么前两层都是 token 维度而不是请求维度。钱是按 token 花的，容量是按 token 撑的，请求次数只是个中间量。

⑥ 下线与切换

被否决的做法是只删资产：模型下架了，已发布的路由、已签发的令牌、正在使用它的智能体还留在原地，变成没人认领的孤儿。

上线下线走的是同一条链：申请通过 → 令牌签发 → ③里那三步网关配置，下线时反着走一遍——先切路由、再收令牌、最后才下架。链断在哪一段，用户就会遇到”申请通过了但调不通”，现象在网关、原因在业务系统，排查起来最费时间。

六段旅程里，④调用和⑤计费必须落在一个流量系统上，①②③⑥的规则最后也要变成这个系统里的配置与数字。下一章的五个判断，就是这个载体的设计约束——它们没有一个是 AI 特有的，AI 只是把它们同时逼到了台前。

三、托住”调用”与”计费”的五个判断

先交代载体是怎么选出来的。市面上的 AI 网关，大部分是拿 API 网关改出来的，APISIX、Kong 都是底座不动，往上叠几个 AI 插件。这条路的代价是模型不是一等公民：它只是”上游服务”的一种类型，不进资产清单、不进成本核算，网关的语言里压根没有”模型”这个词。很多概念在这些网关里看着别扭，根子就在这儿。

另一条路是把模型当一等公民的 AI 原生网关。但它们的扩展点通常是应用层回调或配置项，不是数据面的插件链——LiteLLM 开放的是 Python hook，闭源 SaaS 一般只给配置界面；要按 priority 往请求链路中间插一段，多数还是得自己改源码。

两个约束恰好互相锁死：走可扩展那条路的网关，模型不是一等公民；把模型当一等公民的网关，又不给你在数据面插手的余地。本文这套系统的形状就是被这个死结逼出来的：底座取可扩展的那条路，”模型是一等公民”的那半边语义交给业务控制面去补。 下面五个判断都是这个分工的展开。

3.1 资产链与流量链必须分离

“谁能用什么”和”这次请求怎么转”是两个问题，混在一起的系统最后一定答不好第二个：资产的规则一变，流量路径就得跟着改一次。系统分成三个平面，各自只做一件事：

数据面只负责跑请求。底座是 Apache APISIX，线上跑的是它的商业发行版 API7，插件机制和 priority 规则与开源版一致（开源底座自带 119 个插件）。它不做任何业务判断，只按配置执行插件栈：鉴权、限流、选路、改写、转发、记日志。自研的数据面插件只有两段 Lua（另有 3 个请求改写类自定义插件，属于运维侧配置而非业务逻辑）：

插件 priority 阶段 职责
quota-inject 9000 rewrite 令牌×模型配额注入（仅企业/应用路径，绑 Consumer）
token-guard 1010 rewrite + log 个人令牌鉴权 + 用量上报（个人路径，不建 Consumer）

其余能力全部是底座原生插件加配置编排。代价是受底座版本约束，收益是升级路径清晰、不用维护分叉的网关内核。

配置面是一个独立服务，负责路由模板、模型实例、插件配置、消费者与凭证的下发，核心约束留到 3.5 展开。

业务面管资产和配额，内部还要再分两层，这两层最容易被混为一谈：

层 职责 不做什么
模型资产层 模型注册/上下架、市场与选型、申请审批、令牌签发与权限、用量分账、下线迁移 不碰任何推理流量
配额与分析层 四层限流的配额编排与迁移、调用明细与看板 不决定”谁能申请哪个模型”

资产层回答”谁能用什么”，配额层回答”能用多少”，数据面只认最终下发的那几个配置。三层的输入输出都是明确的结构化数据，任何一层都可以单独回滚。

三个平面只有一条耦合主线：DB 真源 → 插件白名单校验 → JSON Patch 下发 → 回读校验。 业务面要改限流，不能直接碰数据面，每条变更都先落库、再下发，出了问题也能回滚——顺序与规则见 3.5。

3.2 裁决与执行分离，链路只传结论

这个判断是整套限流体系的核心，一句话：

网关不持有配额，只持有配额的结论。

算的地方和数的地方隔着一段距离（见问题一），这段距离怎么填？先看被否决的做法：把配额直接放进网关里计数持有。配额的真源在业务系统，网关会重启、会有多实例，各自为政；要保持一致就得再造一套状态同步，而这套同步恰恰是 3.1 拆掉的东西。于是只剩一条路：业务侧算，数据面数，链路上只传结论。

落成的形态是一条四层链路，每层只做一件事，层与层之间只通过两个变量通信：

这条链路是企业 / 应用调用那一条：令牌对应 APISIX Consumer，注入与计数都在数据面完成。个人调用不走它——先看两个路径为什么互斥。

落点一：两个互斥的路径。企业版走标准方案（key-auth + consumer-restriction 白名单），业务系统负责发凭证；个人版的令牌要在业务系统里做配额、归因到人、按用量计费，而网关手上没有这些数据，于是有了第二个自研插件 token-guard——它其实是业务系统的数据面延伸，真正的配额判定发生在业务系统的 /token-check 内部，数据面只负责把业务错误码 1002 翻译成 HTTP 429。

quota-inject 和 token-guard 分属 rewrite 的两个对象：APISIX 的约定是先跑路由侧 rewrite，再跑 Consumer 侧的非鉴权插件，这一层 priority 同样不跨对象比较。两个插件不在同一条链路上，服务的是两种互斥的调用方：

哪条路走哪边，由网关上的 ai-scene 标签决定，创建路由时强校验互斥：企业版禁 token-guard，个人版禁 key-auth / consumer-restriction。quota-inject 读到的上下文来自 key-auth 产出的 Consumer，不是个人令牌的用户标识；个人路径没有 Consumer，第③④层这种计数型限流取不到注入值、按兜底值 9999999 等于不限流——不过它并不是不设防，闸门换成了 rewrite 阶段那次同步的 /token-check。

落点二：计算与执行彻底分离。配额注入插件的全部逻辑不到 40 行，它只回答”这个令牌调这个模型，该给多少配额”，不数任何请求；真正计数的是 access 阶段的限流插件，两侧唯一的耦合是两个变量名。表达式引擎直接用底座自带的，和路由匹配同一门语法，运维不需要学第二门方言；编译失败直接 500，不让配额静默失效——限流配置出错时宁可拒绝服务，也不能放开额度。

配额变量的插值也是底座原生机制——整条链路是用底座的插值把自己的配额变量喂给底座的计数引擎，自研的只剩中间那个插件。兜底值 9999999 的含义很直白：没算出额度 = 不限流。

落点三：限流是两段式的。一次 token 限流实际发生两次：access 阶段按选中的实例取桶，做一次只读预检——余量至少还剩 1 才放行，本身不扣任何东西；log 阶段等响应回来，拿到本次真实消耗再全额入账。为什么必须两段？因为 token 消耗只有响应回来才知道，而拒绝必须发生在转发之前。access 不预留，log 就得记全额，两段拼起来账目才对得上；access 已经拒绝的请求到不了模型，log 阶段据此跳过入账，避免重复计费。代价也要说清楚：预检只拦”桶已经空了”的请求，在途请求不占额度，并发下实际用量会冲过阈值——这是拿”不预留”换”账目永远按真实消耗记准”。对应的配额可见性头按实例发：X-AI-RateLimit-Limit-<实例名> / Remaining / Reset，客户端能直接看到自己在哪个实例上还剩多少。

落点四：执行顺序。APISIX 的插件生命周期是固定的五段：rewrite → access → before_proxy → header_filter/body_filter → log。关键机制只有一条（排错时不少人栽在这儿）：priority 只在同一个 phase 内比较，值大者先执行，跨 phase 的先后由生命周期决定——所以 quota-inject 的 9000 看起来比 ai-proxy-multi 的 1041 大，但它们分属 rewrite 和 access，不在同一条比较链上。

对用户，这一切最终收敛成两个选项：限流维度 RPM 与 TPM（超出任一即触发）、档位标准模式 / 高性能模式（选高性能需要做架构方案与 ROI 论证），具体数值不在文档里写死，而是在模型市场的模型详情页查。数值会过时，但”去哪查最新值”这个指引不会。

这条判断离开 AI 也成立：任何”配额算在业务侧、计数落在执行侧”的系统，链路上都只能传结论。传状态的方案会立刻撞上同步延迟和丢状态两个问题，而且每个网关实例重启一次就要重新对一次账。

3.3 “这个实例不能用”，只该有一个判断

问题二的解法是把所有”这个实例现在不能用”的判断收敛到一起——否则就是四套互相打架的摘除规则：健康检查刚摘掉的实例，告警系统又给它加了权。

ai-proxy-multi 选路时依次过滤，三层防护共用同一个候选池：

第二层打通了两条原本独立的能力链——选路插件选实例时，会直接回头问限流插件”这个实例还有额度吗”。

于是”配额”成了候选池的过滤条件：高优先级实例额度耗尽，流量自动落到低优先级实例，客户端完全无感。这也正是能力清单里”Fallback 触发策略”那一项想要的效果。ai-proxy-multi 的 priority 是 1041，排在白名单校验（2400）之后、限流计数（1030）之前：先验资格，再选路，最后才计数。

监控告警的自动降权，复用的也是同一个候选池机制。告警接入接口收到 firing 告警时，把对应实例的 priority 置 0，告警前的原值就存在插件自己的字段里，不为一个告警状态单开一张表；resolved 时读回它、恢复原值。因为”优先级为 0”本来就是候选池里的最低档，降权不需要任何特殊逻辑，只是把一个实例排到了队尾。

幂等不是靠锁，是靠状态判据：重复 firing（已是 0 且有备份）、没有备份记录的 resolved、值已经恢复——一律返回 skipped，不报错。多实例的告警状态各存各的，互不干扰。状态要同步落到路由模板、已发布路由、网关三处，用 JSON Patch 改单个字段而不是全量覆盖，并发改配置时谁也不会把谁的改动冲掉；上线时还挂了一个默认关闭的开关做灰度。

底座还支持两个细粒度控制：单次请求最多换几个实例；只对”快速失败”重试——上游卡了 20 秒才报错，这时候再换实例重试，客户端等待时间会翻倍，不如直接把错误返回去。

这条判断和 AI 无关：K8s 的摘流、服务发现的健康实例过滤是同一个形状。AI 带来的新变量只有一个——“不能用”的判据里多了”配额耗尽”这一条，而它恰好是业务侧才知道的信息，所以必须走 3.2 那条”只传结论”的路回来。

3.4 时间是运行时读取的输入，不是定时触发的配置变更

四层限流稳住之后，新需求来了：同一个消费者，忙时（9:00–20:00）限得更严，闲时（20:00–次日 9:00）放开。看着只是”再加一个条件”，但”时间”和模型、令牌都不一样：额度随时刻变，限流配置却靠人改，拿”到点改配置”去表达”随时段变”，问题就来了。

最省事的做法是 crontab 定时批量改配置——但那等于把”时间”变成每天两次的线上配置变更，时段定义在脚本里，批量不一致、PATCH/PUT 覆盖、脚本失败的重试与告警都得自己处理。另一个极端是把时段塞进全局函数，时段定义在函数字符串里，绕开了配置面的真源，也失去了按消费者灰度的能力。两条路的毛病一样：把”时段”变成了配置改动本身。

选定的是第三条：把时段做成请求到来时读取的变量，增量只有约 30 行——加一个时段配置（起止小时，支持跨午夜），时段定义在配置里、可按 Consumer 单独设；rewrite 阶段取当前小时、按顺序匹配时段，把命中的时段写进请求上下文，规则里多加一条”时段 = 忙”的判断，复用的还是同一套表达式引擎和变量插值。零运维，所有消费者在同一秒切换。它成立的前提是那句判断：

时段是请求到来时读取的一个变量，不是到点触发的一次配置变更。

前者原子、可审计、可回滚，后者则要把不一致、覆盖、失败恢复全自己造一遍。

还有一个语义细节：切换那一刻，限流计数器不会清零，切换语义是不对称的——闲 → 忙时，已用掉的额度继续累积，切换瞬间不会成为突破口；忙 → 闲时，余量立刻释放。如果业务要求”切换即清零”，把时段名编进限流的计数键，两个时段天然各用各的计数器。同一需求的两种语义，差别只在计数键的拼法上，这是把”算配额”与”数请求”分开之后白拿的好处。

顺带把它和《大模型网关限流新思路：从进程内漏桶到分布式漏桶矩阵》分清楚：那篇讲的是百炼的总量节流——漏桶搬进 Broker，超限请求 Suspend 排队等几秒，”等总比 429 好”；本节是分账裁决，这个令牌还剩多少额度、超了拦谁，配额是合同承诺，只能拒绝。一个管放行节奏，一个管资格与账目，真要串起来也是先裁决、再排队。

3.5 真源在库，下发只是补丁

问题三的根子——两份真源——前面已经点过。被否决的做法是全量覆盖下发——每次下发都把数据面冲成数据库的样子，运维的手工调整活不过下一次发布；它的近亲是用定时任务批量改线上配置，3.4 已否决过一次。

我的判断落成三条规则：

  1. 受管插件以数据库为唯一真源，按 RFC 6902 生成补丁原子下发；非受管插件一律保留数据面现状，保护运维在数据面手工做的调整。
  2. 网关调用放在数据库事务 Commit 之后。网关是外部 IO，放进事务会让时长不可控；库是真源，真源还没落定就去改下游，失败时无法描述”现在到底是什么状态”。
  3. 下发失败不回滚数据库，回滚顺序恒定：先网关、后库。下发失败多是瞬时原因，记 failed + 告警 + 重试即可恢复一致，回滚是给”改错了”用的，不是给”没送达”用的。顺序和下发正好相反：下发是先立真源、再动执行侧，回滚是先撤执行侧、再撤真源——网关先回到旧状态，错误配置少生效一秒是一秒；库最后回滚，中间断了照旧重试，两边都落定后，下一次下发只会把旧状态推下去。

这三条合起来的形状，和 GitOps 是同一个：声明真源在库，下发只是把差异翻译成补丁，执行侧永远可以被下一次补丁收敛回来。 网关只是把它在一个更刁钻的场景里验证了一遍——补丁的对象是正在跑流量的数据面。

结语

旅程与载体其实在同一个地方交汇：申请通过的那一刻，资产层签发令牌、配额层算出数字、数据面拿到插件配置。从那以后，用户看到的只是”调得通/调不通、快/慢、超没超额”，而这三件事分别由三个平面负责。

如果只保留一句话，我会选这句：

AI 网关的难点从来不是”把请求转给模型”，而是转之前要问清楚”你有没有资格、还剩多少额度”，转之后要回答”这次到底花了多少、算在谁头上”——资格、额度、账，这三件事都发生在模型这条资产链上。

模型是资产，所以资产链必须完整：选型、申请、令牌、调用、计费、下线，缺任何一段就会出现”申请通过了却调不通”或者”下线了却还有令牌在跑”这种两个系统各持一半信息的问题。能力图谱的价值也在这里：每个格子都要能指到具体文件和行号，指不到的就算缺口。

最后要交代的是本文没做到的部分。我在《什么样的网关，才算好的 AI 网关？》里把”数据面性能不可证或运行时行为不安全”列进了一票否决线，按我自己定的标准，这一项我也没过：本文所有结论都是机制与执行顺序层面的逻辑推演，不是性能可证（CPU、GC、p99、火焰图）。功能能跑，不等于跑得动。

作者的话

这套系统从能力盘点、三平面架构设计，到两个自研插件、模型全生命周期、限流迁移与运维台，全程由我一人负责落地。写这篇文章的过程，也是我第一次把散在三个仓库里的实现、加上一份对外的使用手册，拉到同一张图上对照。画完才发现，难的从来不是某个单点能力，而是让”算配额的”、”数请求的”、”管资产的”各待在自己的位置上，再用几条足够笨的规则把它们约束住。

如果你也在做网关二次开发，或者正在被限流、故障转移、配置下发、模型分账这几件事折磨，欢迎交流。

八个能力域分属两条主线：

  • 流量层（A–G）：请求经过时发生了什么
    • A 接入与管理：统一域名与协议入口、多地域、REST 管理面、路由审批与迁移
    • B 路由与负载均衡：model 路由、表达式条件路由、加权与优先级、Fallback、健康检查、N:1 复用
    • C 流量治理与配额：四层限流、令牌×模型双维度、TPM/RPM/并发、配额可见性头
    • D 请求改写与协议：路径重写、认证注入、模型名映射、字段注入、协议转换、流式透传
    • E 认证授权与安全：企业/个人双模式鉴权、消费者白名单、内容审核（预留）
    • F 可观测与分析：40+ 日志字段、Prometheus 指标、链路追踪、明细查询与看板
    • G 高可用与扩展性：Fallback、告警降权、插件白名单与优先级、配置合并
  • 资产层（H）：模型与令牌的生命周期
    • H 模型资产与生命周期：模型市场与上架、族/别名/标签、申请审批、令牌与权限、用量分账、下线迁移

A/B/D/F 是底座给的，E/G 是底座给一半、我补一半，C 要从头拼（见 3.2），H 完全是业务控制面的事（见第二章）。底座对 H 一无所知，这是它与流量层各域最本质的差别——也是”模型不是一等公民”这句话在清单上的样子。

落不到格子里的项即缺口，核对下来还剩这些：

  • 内容审核：能配但管不了——未纳入配置托管、没有管理接口；
  • 可观测：用户/会话维度的 label 与指标缺失，这类分析仍走 ES 双写双查；
  • 协议反向转换：正向已有，OpenAI → Anthropic 的反向转换与 SDK 语义一致性待验证；
  • 并发数分账：手册标注”计划中”，当前只有 Token 维度，预分配额度的成本算不准；
  • 闲忙时段限流：方案已定（见 3.4），落地中，当前全天单档；
  • 底座已有但未接入：响应缓存、Prompt 守卫、MCP 桥接、semantic 路由等，补配置面下发即可。
