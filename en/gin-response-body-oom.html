A postmortem of an OOM caused by caching every response body in a Gin API gateway: why memory ballooned in minutes, and a safer implementation.

Symptom: gateway memory spikes in minutes

We built an API gateway on top of Gin. After deploying it, we found that memory would surge in a short time and then the process would be OOM-killed. The memory trend looked like this:

Zooming in on one occurrence:

In the second chart you can see how fast memory grows: nearly 2 GB in a minute and a half.

For problems where memory spikes this fast, pprof is hard to use — unless you write a script that samples pprof on a timer.

Root cause: every request cached the response body

Another pass over the code turned up the cause:

At a glance, isn’t this the standard way to capture the response body in Gin? After all, this is exactly how it is written on GitHub and Stack Overflow:
https://github.com/gin-gonic/gin/issues/1363
https://stackoverflow.com/questions/38501325/how-to-log-response-body-in-gin

So where is the problem?

Look at the code again: the logic keeps a complete copy of every response body in memory. For requests with large response bodies, that alone causes memory to spike — a log download, for example.

Fix: skip caching by request type

Once the cause was clear, the fix was simple: skip file-download requests based on the response headers, and skip SSE and WebSocket requests based on the request headers — streaming responses are of little value in the audit log, and they also break JSON serialization.

Postmortem: when you copy code, mind your own scenario

The real point of this post is not how the problem was fixed, but this:

  • When you copy code, pay attention to whether it fits your scenario.
  • Use existing wheels whenever you can, instead of building your own.

While hand-writing the API gateway, we also ran into the following:

  • The first version of the network handling was hand-written too, which meant it handled the various Content-Types badly;
  • Because we had to parse the body, and had no bandwidth to support every compression scheme, compression had to be forcibly disabled at the gateway;
  • Hand-written network handling produces strange problems
    • For example: we support a terminal in the browser connecting to a K8S cluster over WebSocket. Suppose the service behind that connection is service A (browser <—-> gateway <—-> service A <—-> K8S cluster). Later, some requests going through the gateway would hit service A directly — skipping the gateway’s API router entirely and reusing the WebSocket connection — even when those APIs did not belong to service A.

We eventually switched to the standard library’s httputil.ReverseProxy for connection handling, and the problem went away.
