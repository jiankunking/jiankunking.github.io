RocketMQ Client DEADLINE_EXCEEDED in the Cloud: Tracing It to Container Memory

Posted on 2023-12-15 Edited on 2026-09-29 Views: Word count in article: 4.4k Reading time ≈ 4 mins.
A RocketMQ Java client failed with gRPC DEADLINE_EXCEEDED only in one cloud test cluster. Packet capture and resource-limit tests traced it to container memory pressure, not the network.

A RocketMQ client started throwing timeouts in a cloud test cluster while the exact same code ran fine locally. This post walks through the investigation, the wrong turns included, and how a gRPC DEADLINE_EXCEEDED turned out to have nothing to do with the network.

Symptoms and the stack trace

A colleague hit a strange one yesterday. After adding RocketMQ consumer code to the service, a program that ran perfectly fine locally started throwing the following exception when deployed to cloud test cluster A1:

Initial investigation: code or network?

My colleague’s first suspicion was the cluster’s network environment. My own first reaction was that it was not the network — why?

Because if it were a network problem, there would be plenty of errors across the cluster, not just from this one service.

So where was the problem? Was it the code?

I compared it against the official demo, and it matched exactly:

https://github.com/apache/rocketmq-clients/blob/master/java/client/src/main/java/org/apache/rocketmq/client/java/example/PushConsumerExample.java

On top of that, another colleague’s identical code ran fine on a different cluster, B1.

Packet capture and the CPU hypothesis

Could it really be a network problem after all?

The exception above was thrown while the service was starting, so it never came up. At that point the container wasn’t ready either — no process to attach to — so we couldn’t yet run a packet capture to rule the network out.

I asked my colleague to move the RocketMQ initialization logic behind an API call, so the service could start normally and I could capture the network traffic. (How to capture packets in a k8s cluster: https://jiankunking.blog.csdn.net/article/details/125189956)

Packet capture screenshot:

The capture shows the network connection being established normally, then the service actively resetting it about 2.7 seconds in — exactly when the exception was thrown.

The packet capture confirmed our suspicion: at least at the TCP level, the network was fine.

Even with that verified, I still deployed the same broken image to cluster B1 — and the problem was still there.

So where was the problem? The investigation stalled.

Along the way I also tried:

  • Switching the RocketMQ address to https://…
  • Toggling enableSsl off and on

…and the problem still wasn’t resolved.

The service’s configuration in the test environment was:

Startup in the test environment took over four minutes. Could too little CPU be the problem — JIT consuming too many resources during startup, preventing the RocketMQ network connection from being scheduled, and causing timeouts?

Raising the CPU limit to 1 core got the service up in under a minute, but the exception remained.

The key clue: not enough memory

The investigation stalled again. Then I remembered:

  1. The container platform injects agents like SkyWalking and Prometheus into our applications by default
  2. In earlier, less rigorous testing, I found that SkyWalking alone occupies 200–300 MB of memory
  3. The java command gets rewritten; the default heap is 65% of the memory limit

800 × 0.65 = 520m, minus 200–300m, leaves roughly 220–320m for the service itself. Could too little memory be the problem?

Raising the memory request/limit step by step to 1200m made the error disappear.

Going back through the exception logs, I noticed that around the time the RocketMQ exception appeared, HikariPool was also failing to create database connections:

HikariPool initializes after the rocketmq init

Repeated verification and the memory threshold

I then told my colleague the fix, assuming that was the end of it…

But that afternoon, he found that the service also started fine with the memory limit put back to 800m. Had something gone differently that morning?

I redeployed the original broken image with the lowered memory limit — and the service really did start normally.

Since the service could now start with the original configuration, how much memory does it actually need when no agents are injected by default?

I first replaced the startup command, removing the injected SkyWalking, Prometheus, and other agents:

The service started fine on 300m.

Then I switched back to the startup command with agents, and found:

  • limit = request = 500m: the service starts normally
  • limit = request = 450m: the exception above reappears
  • limit = request = 400m: the container gets OOMKilled

Conclusions and open questions

Two conclusions are solid by now:

  • The exception was caused by insufficient memory
  • The exact threshold that triggers it remains unclear
    • Two suspects:
      • The memory usage of injected agents like SkyWalking swings significantly with other factors
      • The service’s own memory footprint differed between morning and afternoon runs

I also suspected the cluster was overcommitting memory requests. Checking:

The requests were not overcommitted — the limits were.

Because of time constraints, I have not yet profiled the service’s memory usage or the memory usage of agents like SkyWalking; I will pick that up when I have time.
