APISIX Gateway 504s After Exactly 15 Seconds: Tracing It to tcp_syn_retries

Posted on 2026-10-18 Views: Word count in article: 4.2k Reading time ≈ 4 mins.
An API gateway kept returning 504s with request time pinned at exactly 15 seconds. This postmortem walks through timeout tracing, kernel parameter analysis, DNS elimination and packet capture to root-cause it as a SYN retransmission timeout.

Our production API gateway (API7 Enterprise, a commercial distribution of Apache APISIX) started returning intermittent 504s. Every single one of those requests took exactly 15 seconds. Not 14, not 16 — 15.

The plugin timeout was configured at 600 seconds, so the application layer had no reason to give up that fast. Where does 15 seconds come from? This post walks through how we narrowed it down to tcp_syn_retries=3 and a SYN retransmission timeout — and why we deliberately did not ship the obvious fix.

Following the timeout through the code

Three layers of evidence

layer evidence conclusion
application 717 requests with request_time = 15s timeout is pinned at exactly 15s, not at 600s
code source trace: 600s propagates correctly not an application timeout
network PCAP: SYN retransmit gaps of 1s, 3s, 7s kernel SYN retransmission timeout

All three layers point to the same root cause: tcp_syn_retries=3 combined with SYNs that never got answered.

The fix we did not ship

The tempting fix — bumping tcp_syn_retries to 5 — was rejected on purpose.

It treats the symptom, not the disease:

  1. The root cause stays. Why are the SYNs not getting through, or not getting answers? Something at the network level is broken. Retrying more often does not repair it.
  2. Failure just takes longer. tcp_syn_retries=5 stretches the total timeout from 15s to 63s. Users now wait over a minute to learn the same thing. That is a worse experience, not a better one.
  3. It hides the real problem. A longer timeout makes the symptom recede from dashboards and alerts while the underlying connectivity issue keeps getting worse.

The correct directions: fix connectivity at the network layer, or implement retry/fallback in the application layer where you control backoff, budgets and error semantics — rather than depending on kernel-level retries you cannot observe or tune per-request.

We followed up by pulling in the corporate network team for a deeper investigation of the network layer. That is where the actual fix lives.

Takeaways

  • Odd, round timeout values are a fingerprint. 15s, 31s, 63s are almost never application configuration. They are the kernel telling you its retry budget expired. tcp_syn_retries=N yields total timeouts of 1s, 3s, 7s, 15s, 31s, 63s for N = 0…5.
  • Cross-validate across layers. Logs alone suggested DNS. Source code alone exonerated the application. Packet capture alone showed retransmissions but not their business impact. Only the combination — request-duration histograms from logs, source-level timeout tracing, and PCAP — pinned the root cause.
  • Similar-looking errors can be unrelated. The DNS failures and the SYN timeouts appeared in the same gateway, in the same period, but had completely different duration profiles. Always compare distributions, not anecdotes.
  • A retry knob is not a fix. If you cannot explain why packets are being dropped, more retries just convert a fast failure into a slow one.

The gateway in this incident is API7 Enterprise, a commercial distribution of Apache APISIX. The fix discussed above was deliberately not applied; connectivity was escalated to the network team instead.
