Why APISIX Gateway 504s Clustered Around 15 Seconds: A SYN Timeout Investigation

Our production API gateway (API7 Enterprise, a commercial distribution of Apache APISIX) started returning intermittent 504s. The failed requests clustered around 15 seconds.

The plugin timeout was configured at 600 seconds, so where did the 15 seconds come from? The kernel exhausted its SYN retransmission budget without seeing a SYN-ACK. The tcp_syn_retries=3 setting explained the timing; why the SYN-ACK never arrived remained an open question.

Following the timeout through the code

First step: verify that the 600-second timeout actually reaches the bottom of the stack. Tracing the call chain from the plugin configuration, through the Lua layer, through the FFI boundary, into the C module:

The 600s value is passed down correctly, and the C module really does arm a 600s timer. So the timeout is not coming from the application. Something else owns the 15-second deadline.

Eliminating DNS

Could this be DNS resolution failing slowly? Looking at APISIX's DNS resolution code for the error message formats:

Searching the gateway logs for these strings did turn up DNS errors:

But when we pulled the request_ids of those DNS errors from our log store and compared the two populations, a clear difference emerged:

count 21 750
avg duration 2.25s 15.38s
status code 500 504

The DNS failures returned 500s and averaged 2.25 seconds. They were a separate group from the 504s clustered around 15 seconds.

Packet capture

Theory is nice; packets are better. Capturing traffic on the gateway node and filtering for handshakes:

Here is one captured retransmission sequence. The elapsed times are measured from the initial SYN:

Successive sends were about 1, 2, and 4 seconds apart, consistent with the exponential backoff in this environment. With no response, the sequence predicts a further wait of about 8 seconds after the final send before the connection attempt ends.

Three layers of evidence

layer evidence conclusion
application these 504 requests averaged 15.38s requests failed after about 15s
code source trace: the 600s deadline reaches the C module the configured plugin deadline had not expired
network PCAP: successive SYNs about 1s, 2s, and 4s apart consistent with the observed SYN retransmission sequence

Together, the evidence shows where the timeout happened and explains the roughly 15-second wait. The capture did not establish why the gateway got no SYN-ACK.

The fix we did not ship

We decided against bumping tcp_syn_retries to 5. Under the same backoff schedule, and with no response, it would stretch the wait from about 15s to about 63s.

We asked the network team to investigate connectivity. Application-level retries or fallback, within the request's time budget, could also limit the impact of this kind of failure.

Takeaways

  • A cluster of timeouts around the same duration is a clue. Compare the timing against the application's configured deadline and the retransmission schedule observed in the capture.
  • Cross-check across layers. Request logs, source-level timeout tracing, and the packet capture together identified the timeout as a TCP connection failure. Finding why the connection could not be established required further network investigation.
  • Similar-looking errors can be unrelated. The DNS failures and the SYN timeouts appeared in the same gateway, in the same period, but had completely different duration profiles. Always compare distributions, not anecdotes.
  • Check what a retry setting changes. With no response, a higher retry count only extends the wait.

The gateway in this incident is API7 Enterprise, a commercial distribution of Apache APISIX. The fix discussed above was deliberately not applied; connectivity was escalated to the network team instead.
